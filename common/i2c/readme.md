# TinyI2CMaster I2C driver - User Manual

## Overview

The TinyI2CMaster library provides I2C (Two-Wire Interface / TWI) master functionality for ATtiny microcontrollers. It enables communication with I2C slave devices such as sensors, display modules, and other peripherals using the standard I2C protocol.

This is a **master-only** implementation, meaning your ATtiny acts as the I2C master controlling slave devices on the bus. The library uses bit-banging (software implementation) to generate I2C protocol signals.

**Key Capabilities:**

- Standard (100 kHz) and fast (400 kHz) I2C modes
- START, REPEATED START, and STOP condition generation
- Byte-level read and write operations
- Automatic clock stretching handling
- Blocking (non-interrupt) operation

---

## Features

- ✅ **Master-only I2C implementation** - Controls I2C transactions
- ✅ **Dual speed modes** - 100 kHz (standard) and 400 kHz (fast)
- ✅ **Protocol compliance** - Full I2C bus protocol support
- ✅ **Clock stretching** - Handles slaves that hold SCL low
- ✅ **Simple API** - Easy-to-use read/write functions
- ✅ **ATtiny compatible** - Works with ATtiny45, ATtiny85, ATtiny84, and other models
- ✅ **No interrupts** - Blocking operations simplify integration
- ✅ **Address acknowledgment** - Detects if slaves are present

## Hardware Setup

### I2C Bus Overview

The I2C bus consists of two open-drain signal lines:

- **SCL (Serial Clock):** Generated by the master to synchronize communication
- **SDA (Serial Data):** Bidirectional line for data transfer

Both lines require pull-up resistors (typically 4.7 kΩ to 10 kΩ) to pull the signals high when idle.

### Wiring Requirements

| Component               | Purpose                                            |
|-------------------------|----------------------------------------------------|
| SCL line                | Clock signal from master (ATtiny) to slave devices |
| SDA line                | Data signal between master and slave devices       |
| Pull-up resistor on SCL | 4.7 kΩ to 10 kΩ to VCC                             |
| Pull-up resistor on SDA | 4.7 kΩ to 10 kΩ to VCC                             |
| GND                     | Common ground between all devices                  |

### ATtiny Pin Configuration

Pin assignments vary by ATtiny model. Common configurations:

**ATtiny84:**

```text
SCL: PA4 or PA6
SDA: PA5 or PA7
```

**ATtiny45/85:**

```text
SCL: PB2
SDA: PB0
```

Check your specific ATtiny datasheet for exact pin assignments.

### Example Wiring Diagram

```text
ATtiny84          I2C Slave (e.g., Nunchuk)
  +5V                   +3.3V
   |                    |
   ├──[4.7k]──┬────┐    |
   |          |    |    |
   |         SCL   GND  |
   |          |         |
   ├──[4.7k]──┬────┤    |
   |          |    |    |
   |         SDA   +3.3V
   |          |
  GND────────GND──────GND
```

**Note:** Some I2C devices run on 3.3V, others on 5V. Verify your slave device voltage requirements and add level shifters if needed when mixing voltages.

## Getting Started

### 1. Include the Library

```cpp
#include <TinyI2CMaster.h>
```

This makes the `TinyI2C` global object available for I2C operations.

### 2. Initialize the Bus

In your setup code, call `init()` to configure the I2C bus:

```cpp
void setup() {
    // Initialize in standard mode (100 kHz)
    TinyI2C.init(false);
}
```

Or for fast mode (400 kHz):

```cpp
TinyI2C.init(true);  // Fast mode: 400 kHz
```

### 3. Perform I2C Transactions

A typical I2C transaction follows this pattern:

```cpp
// Start communication with slave at address 0x52 in write mode
if (TinyI2C.start(0x52, 0)) {
    // Slave acknowledged
    
    // Write data
    TinyI2C.write(0xFA);  // Send command
    
    // End transaction
    TinyI2C.stop();
} else {
    // Slave did not acknowledge (not present or not responding)
}
```

### 4. Main Loop Pattern

```cpp
void loop() {
    // Perform I2C operations
    if (TinyI2C.start(0x52, 2)) {  // Read 2 bytes
        uint8_t byte1 = TinyI2C.read();      // Read first byte
        uint8_t byte2 = TinyI2C.readLast();  // Read last byte (sends NACK)
        TinyI2C.stop();
    }
    
    _delay_ms(50);  // Typical polling interval
}
```

## API Reference

### Initialization

#### `void init(bool fast = false)`

Initializes the I2C master bus and configures the I2C control registers.

**Parameters:**

- `fast` (optional):
  - `false` (default): Standard mode (100 kHz)
  - `true`: Fast mode (400 kHz)

**Notes:**

- Must be called once before any I2C communication
- SCL and SDA pins must have pull-up resistors
- The actual frequency depends on the ATtiny clock frequency

**Example:**

```cpp
void setup() {
    TinyI2C.init();      // Standard mode
    // or
    TinyI2C.init(true);  // Fast mode
}
```

---

### Starting Transactions

#### `bool start(uint8_t address, uint8_t readcount)`

Generates an I2C START condition and addresses a slave device.

**Parameters:**

- `address` (7-bit): Slave address (0x00-0x7F)
- `readcount`:
  - `0`: Write mode (R/W bit = 0)
  - `> 0`: Read mode (R/W bit = 1)

**Returns:**

- `true`: Slave acknowledged the address
- `false`: Slave did not acknowledge (not present or not responding)

**Notes:**

- This function automatically adds the R/W bit to the address
- For a 7-bit address 0x52:
  - Write: internally becomes 0xA4 (0x52 << 1 | 0)
  - Read: internally becomes 0xA5 (0x52 << 1 | 1)

**Example:**

```cpp
// Write to slave at 0x52
if (TinyI2C.start(0x52, 0)) {
    // Slave acknowledged
}

// Read from slave at 0x52
if (TinyI2C.start(0x52, 2)) {
    // Slave acknowledged, preparing to read 2 bytes
}
```

---

#### `bool restart(uint8_t address, uint8_t readcount)`

Generates a REPEATED START condition to switch between transactions without releasing the bus.

**Parameters:**

- `address` (7-bit): New slave address (0x00-0x7F)
- `readcount`: Read count (same as `start()`)

**Returns:**

- `true`: Slave acknowledged the address
- `false`: Slave did not acknowledge

**Notes:**

- More efficient than `stop()` + `start()` as it keeps bus control
- Useful for write-then-read sequences with the same slave
- Required when changing I2C bus direction mid-transaction

**Example:**

```cpp
// Send command, then read response from same slave
TinyI2C.start(0x52, 0);
TinyI2C.write(0xFA);  // Send command

TinyI2C.restart(0x52, 6);  // Switch to read mode
uint8_t data[6];
for (int i = 0; i < 5; i++) {
    data[i] = TinyI2C.read();      // Read with ACK
}
data[5] = TinyI2C.readLast();      // Last byte gets NACK

TinyI2C.stop();
```

---

### Reading Data

#### `uint8_t read(void)`

Reads one byte from the slave and sends ACK (acknowledgment).

**Returns:** 8-bit data byte received from slave

**Usage:** Use for all bytes except the last one in a read sequence.

**Notes:**

- Automatically sends ACK signal after the byte
- Tells the slave more bytes are expected
- Blocks until byte is received or timeout

**Example:**

```cpp
TinyI2C.start(0x52, 3);  // Read 3 bytes
uint8_t b1 = TinyI2C.read();      // Byte 1 (ACK sent)
uint8_t b2 = TinyI2C.read();      // Byte 2 (ACK sent)
uint8_t b3 = TinyI2C.readLast();  // Byte 3 (NACK sent)
TinyI2C.stop();
```

---

#### `uint8_t readLast(void)`

Reads one byte from the slave and sends NACK (Not Acknowledged).

**Returns:** 8-bit data byte received from slave

**Usage:** Use for the final byte in a read sequence.

**Notes:**

- Automatically sends NACK signal after the byte
- Tells the slave this is the last byte being read
- Bus is ready for `stop()` or `restart()` after this call
- Blocks until byte is received or timeout

**Example:**

```cpp
TinyI2C.start(0x52, 1);           // Read 1 byte
uint8_t data = TinyI2C.readLast(); // Read with NACK
TinyI2C.stop();
```

---

### Writing Data

#### `bool write(uint8_t data)`

Writes one byte to the slave and waits for acknowledgment.

**Parameters:**

- `data`: 8-bit value to send to slave

**Returns:**

- `true`: Slave acknowledged (pulled SDA low)
- `false`: Slave did not acknowledge (transmission failed)

**Notes:**

- Sends MSB first
- Automatically waits for slave ACK/NACK signal
- Returns after receiving acknowledgment or timeout

**Example:**

```cpp
TinyI2C.start(0x52, 0);
if (TinyI2C.write(0xFA)) {
    // Slave acknowledged the command
} else {
    // Slave did not acknowledge
}
TinyI2C.stop();
```

---

### Ending Transactions

#### `void stop(void)`

Generates an I2C STOP condition and releases the bus.

**Notes:**

- Terminates the current I2C transaction
- Returns the bus to idle state
- Must be called at the end of every transaction
- After `stop()`, call `start()` to begin a new transaction

**Example:**

```cpp
TinyI2C.start(0x52, 0);
TinyI2C.write(0x42);
TinyI2C.stop();  // Transaction complete
```

## Complete Examples

### Example 1: Simple Write

Write a single command byte to a slave device.

```cpp
#include <TinyI2CMaster.h>
#include <util/delay.h>

void setup() {
    TinyI2C.init(false);  // Standard mode
}

void loop() {
    // Send 0xFA command to device at 0x52
    if (TinyI2C.start(0x52, 0)) {
        if (TinyI2C.write(0xFA)) {
            // Success: write and ACK received
        }
        TinyI2C.stop();
    } else {
        // Device not responding
    }
    
    _delay_ms(100);
}
```

### Example 2: Write Then Read

Send a command, then read response data.

```cpp
#include <TinyI2CMaster.h>
#include <util/delay.h>

void setup() {
    TinyI2C.init(false);  // Standard mode
}

void loop() {
    // Send command, then read 6 bytes
    if (TinyI2C.start(0x52, 0)) {
        // Send command
        TinyI2C.write(0xFA);
        
        // Switch to read mode with repeated start
        if (TinyI2C.restart(0x52, 6)) {
            // Read 6 bytes
            uint8_t data[6];
            for (int i = 0; i < 5; i++) {
                data[i] = TinyI2C.read();      // Read with ACK
            }
            data[5] = TinyI2C.readLast();      // Last byte with NACK
            
            // Process data...
        }
        TinyI2C.stop();
    }
    
    _delay_ms(50);
}
```

## Typical Use Cases

### Use Case 1: I2C Sensor Reading

Reading acceleration or temperature data from an I2C sensor.

```cpp
void read_sensor_data() {
    if (TinyI2C.start(0x52, 6)) {  // 6-byte sensor data
        uint8_t data[6];
        for (int i = 0; i < 5; i++) {
            data[i] = TinyI2C.read();
        }
        data[5] = TinyI2C.readLast();
        TinyI2C.stop();
        
        int16_t x = (data[0] << 2) | ((data[5] >> 2) & 0x03);
        int16_t y = (data[1] << 2) | ((data[5] >> 4) & 0x03);
        int16_t z = (data[2] << 2) | ((data[5] >> 6) & 0x03);
        
        // Use x, y, z values...
    }
}
```

### Use Case 2: I2C Device Configuration

Writing configuration registers to an I2C device.

```cpp
void configure_device() {
    if (TinyI2C.start(0x48, 0)) {
        TinyI2C.write(0x01);  // Register 1
        TinyI2C.write(0x80);  // Config value
        TinyI2C.stop();
    }
}
```

### Use Case 3: I2C Device Polling

Periodically checking device status from multiple I2C slaves.

```cpp
void poll_devices() {
    // Poll device 1
    if (TinyI2C.start(0x52, 1)) {
        uint8_t status = TinyI2C.readLast();
        TinyI2C.stop();
        
        if (status & 0x01) {
            // Handle event...
        }
    }
    
    // Poll device 2
    if (TinyI2C.start(0x48, 1)) {
        uint8_t status = TinyI2C.readLast();
        TinyI2C.stop();
        
        if (status & 0x02) {
            // Handle event...
        }
    }
}
```

## Troubleshooting

### Device Not Detected

**Symptom:** `start()` always returns `false`

**Possible Causes:**

1. **I2C bus not initialized** - `init()` not called
2. **Wrong slave address** - Check device datasheet
3. **Wiring issues** - Check SCL/SDA connections
4. **Missing pull-up resistors** - Both SCL and SDA need pull-ups
5. **Device power problem** - Verify slave device is powered
6. **I2C pins misconfigured** - Verify SCL/SDA pin mappings

**Solutions:**

- Verify `TinyI2C.init()` is called in `setup()`
- Double-check slave address (usually 7-bit: 0x00-0x7F)
- Use a multimeter to verify 5V/3.3V on pull-up resistors
- Check continuity of SCL and SDA wires
- Verify slave device is powered and not in reset
- Review ATtiny datasheet for I2C pin assignments

### Bus Hangs

**Symptom:** Program appears to freeze during I2C operation

**Possible Causes:**

1. **Slave holding SCL low** - Clock stretching issue
2. **Infinite wait on ACK** - Slave not responding
3. **No timeout mechanism** - Library waits indefinitely
4. **Wiring short circuit** - SCL/SDA shorted to GND or VCC

**Solutions:**

- Check if slave is in clock stretching mode
- Verify slave device is not in error state
- Add a watchdog timer to force reset if needed
- Inspect PCB for shorts or damaged traces

### Read/Write Failures

**Symptom:** `write()` returns `false` or incorrect data is read

**Possible Causes:**

1. **I2C mode mismatch** - Fast mode with slow slave
2. **Bus noise/interference** - EMI on I2C lines
3. **Wire length too long** - Capacitance affecting signal integrity
4. **Incorrect read/write sequence** - Wrong use of `read()` vs `readLast()`

**Solutions:**

- Try standard mode (100 kHz) instead of fast mode
- Keep I2C wires short and twisted together
- Add ferrite beads or series resistors (470Ω) to SCL/SDA
- Verify correct byte order and read sequence
- Check that `readLast()` is used for the final byte

### Intermittent Communication

**Symptom:** I2C operations work sometimes but fail other times

**Possible Causes:**

1. **Insufficient power delivery** - Weak power supply
2. **Environmental noise** - EMI from nearby circuits
3. **Temperature sensitivity** - Bus timing affected by temperature
4. **Loose connections** - Intermittent contact on I2C lines

**Solutions:**

- Add capacitors (100 nF) near slave device power pins
- Move I2C wires away from high-current paths
- Shorten I2C bus lines if possible
- Try slower I2C speed (standard mode)
- Tighten all connections and solder joints

## Performance Considerations

### I2C Timing

**Standard Mode (100 kHz):**

- Byte transfer time: ~90 µs
- 6-byte read: ~540 µs + overhead

**Fast Mode (400 kHz):**

- Byte transfer time: ~22 µs
- 6-byte read: ~130 µs + overhead

### ATtiny Blocking

All I2C operations are **blocking** - the CPU waits for I2C to complete before continuing. This means:

- No other code runs during I2C transfers
- Timing-critical code may be affected
- Typical I2C operations take 1-2 ms

For timing-sensitive applications, keep I2C operations short and frequent.

### Pull-Up Resistor Selection

Pull-up resistor value affects:

- **Smaller resistors (4.7 kΩ):** Faster edges, lower propagation delay, more current draw
- **Larger resistors (10 kΩ):** Slower edges, higher propagation delay, less current

Typical values: 4.7 kΩ for standard use, up to 10 kΩ for low-power applications.

## I2C Protocol Overview

For reference, here's a basic outline of I2C protocol operations:

**START Condition:** SDA goes LOW while SCL is HIGH
**STOP Condition:** SDA goes HIGH while SCL is HIGH
**Data Bit:** SCL LOW, set SDA, then SCL HIGH, then read SDA
**ACK:** Master pulls SDA LOW for one clock cycle
**NACK:** Master releases SDA (goes HIGH) for one clock cycle

## Support & Tips

- **Verify addresses:** Use an I2C scanner sketch to detect all devices on the bus
- **Test at slow speed:** Start with standard mode (100 kHz) before trying fast mode
- **Use bypass capacitors:** Add 100 nF ceramic capacitors near slave device power pins
- **Keep wires short:** Long I2C wires increase capacitance and propagation delay
- **Match voltage levels:** Use level shifters if mixing 3.3V and 5V devices

---

## Limitations

- **Master-only:** Cannot operate as an I2C slave
- **Blocking operations:** No non-blocking async I2C
- **No interrupt support:** All operations are polling-based
- **Single instance:** Only one `TinyI2C` object available
- **8-bit address only:** Full byte addressing, not 10-bit extended addressing
